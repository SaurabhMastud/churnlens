# Architecture — ChurnLens

## Why this project

Retention is the metric subscription businesses are judged on, and the analysis
around it is unusually easy to get quietly wrong. Cohort retention tables,
survival curves and "churn driver" models are standard output in analytics
roles, yet most published examples are unverifiable: they compute a number from
a dataset whose true churn process is unknown, so there is no way to tell a
correct analysis from a plausible-looking one.

ChurnLens inverts that. Subscriber lifecycles are **generated from a known
hazard model** — churn probability is an explicit function of plan tier,
tenure and engagement, with coefficients fixed in configuration. The ground
truth is therefore available, and every analysis in the project can be checked
against it: a Kaplan–Meier curve can be compared to the hazard it was drawn
from, and a churn-driver model can be asked whether it recovers the planted
coefficients and their ordering.

That is the point of the project. Week 01 (RetailPulse) was pipeline
engineering, where correctness means data arrives intact. Here correctness
means an *inference* is right, which needs a different kind of test — and
having ground truth is what makes those tests possible rather than decorative.

## Components

| Component | Tool | Role |
|---|---|---|
| Lifecycle generator | Python (`src/generate`) | Synthetic subscribers with churn drawn from an explicit, configured hazard model — the ground truth |
| Store | DuckDB (`data/`) | Subscribers, subscription months, engagement events |
| Sanity report | Python + SQL (`src/report`) | Read-only first look: cumulative churn by plan, monthly hazard by tenure bucket |
| Cohort analysis | Python + SQL (`src/cohorts`) | Signup-cohort retention matrix, pooled and per-plan retention curves |
| Survival analysis | Python + SQL (`src/survival`) | Kaplan–Meier curve with Greenwood/log-log intervals, log-rank across plans |
| Driver model | scikit-learn (`src/drivers`) | Churn driver estimation, scored against the planted coefficients |
| Segments | Python + SQL (`src/segments`) | Survival by observed-activity segment, honest and look-ahead cuts side by side |
| LTV | Python (`src/ltv`) | Restricted expected value per subscriber, by plan and segment |
| Dashboard | Streamlit (`dashboard/app.py`) | Five tabs over the analyses: retention matrix, survival, drivers, segments, value. No SQL of its own |
| Reports | `docs/` | Day-7 architecture report and IEEE paper |

## Data flow

```
hazard config (known coefficients)
        |
        v
src/generate  -->  data/churnlens.duckdb
                     |
                     |  analysis-facing
                     |-- subscribers         (plan, signup month, churn month, censoring)
                     |-- subscription_months (one row per subscriber-month, active or churned)
                     |-- engagement_events   (logins/feature use, the observable signal)
                     |-- run_meta            (window length, count, seed -- provenance)
                     |
                     |  quarantined -- tests only, never read by an analysis
                     |-- hazard_truth        (the planted coefficients)
                     |-- subscriber_truth    (each subscriber's latent engagement level)
                               |
                   src/report, src/cohorts, src/survival (drivers: day 4)
                   read only the analysis-facing tables
                               |
                   Streamlit dashboard + day-7 reports
```

## The ground-truth contract

The generator writes the coefficients it used into the store alongside the
data. Analyses never read them; tests do. This keeps the analysis honest — it
cannot accidentally be tuned against the answer — while still allowing a test
to assert that the estimate lands within tolerance of the truth.

This is the project's central design decision and the reason the test suite can
say anything meaningful about analytical correctness.

**The store is split in two by this contract.** `hazard_truth` and
`subscriber_truth` are quarantined; `subscribers`, `subscription_months` and
`engagement_events` are analysis-facing. Two things enforce the split, in that
order of strength:

1. **Structurally** — the truth is not in the tables an analysis queries, so
   there is nothing to read. This is what day 2 bought by moving the latent
   engagement level off `subscribers`.
2. **By test** — a guard walks each analysis module's AST and fails if it names
   a quarantined table or a latent column. It discovers analysis modules by
   convention rather than by a hand-maintained list, so a module added on day 3
   or 6 is covered without anyone remembering to opt it in. Discovery spans
   `src/` *and* `dashboard/`, and a further test fails if Python appears in a
   directory in neither list — a guard is only as wide as the places it looks,
   and the day-6 Streamlit app would otherwise have sat outside it.

Day 1 shipped only the second of these, and only for one module, which is why
the latent level was readable at all. The lesson generalises: a contract held
up by a test that someone has to remember to extend is one module away from
being held up by nothing.

## Decisions log

- **Synthetic data with a known hazard, not a public churn dataset**: a public dataset has real messiness but no ground truth, so no analysis built on it can be verified — only sanity-checked. Since the project's goal is testable analytics, verifiability wins. The cost is that the data lacks real-world pathologies, which is recorded as a limitation rather than hidden.
- **Coefficients stored with the data but never read by the analysis**: the alternative — passing the truth into the analysis for comparison — would make it trivially possible to fit to the answer. Keeping the channel one-way (tests may read, analyses may not) is what makes the comparison evidence.
- **DuckDB again, deliberately**: the same reasoning as week 01 (no server, real SQL, good pandas interop) and it keeps the week's novelty in the analysis rather than in infrastructure setup. Not every project needs a new database.
- **The day-1 pins described an environment nobody had built**: `requirements.txt` was written on day 1 from memory and never installed from. Checked against the live interpreter, five of nine pins had drifted (duckdb 1.0.0 vs 1.5.5 installed, pandas 2.2.2 vs 2.3.3, numpy 1.26.4 vs 2.4.6, scikit-learn 1.5.1 vs 1.9.0, pytest 8.3.2 vs 9.1.1) and `statsmodels` was pinned but not installed at all. That makes `pip install -r requirements.txt` produce an environment the suite had never run in — a portfolio repo's most embarrassing kind of broken, because it fails for the reader and not for the author. Re-pinned to the versions actually verified (Python 3.11.9), with the not-yet-imported packages kept in a labelled section so the file states plainly what has been exercised and what has not. `statsmodels` was dropped rather than carried at an unverified version; scikit-learn covers the day-4 driver model, and if statsmodels turns out to fit better it gets added at a version that has been run. This also matters more than it did yesterday: `pandas` became a hard runtime import of `src/store` with the bulk-load change, so it is no longer only an analysis dependency.
- **The ground-truth contract is enforced by a test, not by convention**: "analyses must not read `hazard_truth`" is a comment in every file, which is worth nothing once there are six modules and a dashboard. `test_the_report_never_reads_the_ground_truth` walks the report module's AST and asserts no string literal it executes names the table and that it does not import `src.hazard`. Deliberately AST-based rather than a substring scan of the source: the module explains the contract in its own docstring, so a text scan would fail on prose while missing nothing real. Docstrings are excluded, f-string fragments are included (that is how the bucketed query is assembled), and a second test asserts the check can still see the queries that *are* there, so it cannot pass by being broken. Verified by adding a `hazard_truth` read to the report, which fails it.
- **The dashboard does nothing at import time**: every Streamlit call lives in a function and the entry point is guarded. Two reasons, both concrete - the contract test imports the module to walk its AST, so an import with side effects would mean the test suite was rendering a dashboard, and `streamlit run` executes the file as `__main__` either way, so the guard costs nothing. A test asserts the module body contains no bare expression statements, which is what a stray `st.title(...)` would be.
- **No dashboard-specific SQL, at all**: every figure on the page comes from the same functions the CLI reports call. A query written twice can disagree with itself, and the copy in a dashboard is the one nobody tests. The reshaping between an analysis function and a chart is the only new code, and that is where the tests point.
- **No plotting library was added.** Streamlit's own `line_chart` / `bar_chart` / `dataframe` cover everything here. The retention matrix is a table of percentages rather than a colour heatmap specifically because a gradient-styled DataFrame pulls in matplotlib, and that is a large dependency for cell shading. Recorded as a trade rather than left as a silent omission. Unreachable cells arrive as NaN and render blank, so day 2's rule survives into the UI - a test walks the frame and fails if any unreachable cell is a zero.
- **The two retention estimators are plotted together, on one convention**: cohort retention at tenure t and Kaplan-Meier's S(t-1) are the same quantity, so the frame applies that offset. Plotting S(t) against retention(t) would draw two lines a month apart and invite a reader to explain a gap that is purely a convention. Showing only one of them would hide that there are two ways to compute it.
- **A health probe is not a smoke test, and finding that out was worth the detour.** `streamlit run --server.headless true` plus `GET /_stcore/health` answers `ok` in about three seconds - and proves only that the web server started. Streamlit runs the script per *session*, when a client connects over a websocket; with no client attached the script never executes, so a page that would crash on its first line still returns 200. `streamlit.testing.v1.AppTest` runs the script the way a session does and exposes what it raised, which is the check worth having. Week 01 had to record an Airflow DAG that was never executed as a limitation; this is that lesson applied one week later.
- **The store path comes from `CHURNLENS_STORE`**: `streamlit run` owns the command line, so a flag was not available, and a dashboard that can only open one hardcoded path is awkward to deploy and impossible to test without depending on a built store lying in the working directory. One environment variable, defaulting to the same path as before.
- **A real crash found by running the app: the horizon slider could be dragged past the data.** The slider was a hardcoded 3-24 months. On a store with a shorter window, every cell of the value grid was then skipped, the grid came back empty, and `pandas.pivot` raised `KeyError: 'plan'` - an error about a missing column when the actual problem was a horizon outside the observed data. Fixed at both ends, which is the root-cause version rather than the symptom version: the slider's maximum now comes from the store's own window, and `ltv.by_plan_and_activity` refuses an impossible horizon with a message that names it, matching what `by_plan` already did. Skipping a thin cell is reasonable; returning an empty grid was not.
- **The guard fired on honest prose twice, so the guard changed rather than the prose.** `\bengagement\b` over every string literal flagged a line in `src/segments` explaining that engagement dominates plan, and a dashboard caption explaining that the engagement coefficient comes back attenuated. The first fix was to reword the output, and it made the output worse - the caption had to avoid the clearest word for the thing it described. A guard that degrades the product to stay green has a bug in it, so the latent-column check narrowed to *query-shaped* strings (`select ... from`), since a latent column can only be read through a query. The table-name check is deliberately **not** narrowed: `subscriber_truth` is a proper noun with no reason to appear in prose. A mutation test covers the obvious exploit - a query that discusses the column in a SQL comment and also reads it - and it is still caught twice over.
- **Segmenting on activity is the most dangerous cut in the project, and the danger is in the definition rather than the arithmetic**: "group subscribers by their average monthly activity, then compare retention" is the natural phrasing and it looks into the future - a subscriber's average is taken over months that exist only because they had not churned yet, so the segment is partly the outcome. Same family as immortal-time bias. The honest cut is a covariate known at entry: **first-month activity**, which everyone has. Both are computed and the naive one is printed beside the honest one, labelled, because a reader who has seen it done the wrong way should be able to see how much it mattered. Measured across five store configurations rather than the first one tried: the look-ahead cut inflates the top-to-bottom S(11) gap by 1.13x / 1.25x / 1.31x / 1.26x / **1.54x** (the committed store), and at the shallower tenure 5 by only 1.02x. The effect grows with window length, since a longer window gives the lifetime average more months in which to encode survival - so quoting the committed store's 1.54x as a general figure would be overstating, and the test asserts a floor of 1.05 with the whole range in its docstring.
- **A real non-determinism bug in the segment assignment**: baseline activity is an integer event count, so hundreds of subscribers share a value and the quartile boundary falls *inside* a tie. With `ntile(4) over (order by activity)`, which subscribers landed either side of that boundary depended on scan order, and the same store gave S(11) for basic/A1 as 66.1% on one run and 65.9% on the next. Small, and fatal to the point of the project: an analysis nobody can reproduce cannot be checked. Fixed by breaking the tie on `subscriber_id` - still arbitrary, now deterministic and stated in the docstring rather than hidden.
- **The accumulator became part of the survival module's interface** rather than being copied. `src/segments` needs risk tables segmented by a subscriber-level derived attribute, which is one join and a window function beyond what `survival.risk_table` is built for, so it writes its own query - but it feeds the rows through `survival.accumulate`, so the Greenwood variance and the log-log transform exist once. A second copy in the segment module is exactly where the two would have drifted. A test reconciles the segmented risk tables against the pooled one cell by cell, in both the plain and the per-plan form, since two queries that are supposed to count the same risk set are the natural place for a quiet disagreement.
- **LTV is reported as a *restricted* expected value with the horizon attached to the number**: survival is still 75.9% when the window closes, so a "lifetime" figure requires extrapolating the tail - an assumption, not a measurement. `by_plan` refuses a horizon longer than the observed curve rather than extrapolating silently. Prices are stated as an assumption (they are not in the store and cannot be estimated from it), overridable on the CLI, and every figure scales linearly in them - which a test asserts, because the output claims it.
- **The `price / churn_rate` shortcut, measured in both of its forms.** Truncated to the same horizon it is close but not neutral: the pooled rate averages a hazard running from 4.2% down to 1.3%, so over a horizon shorter than the averaging window it under-prices early risk and **over-states** value by +3.6% / +3.0% / +1.5% at 12 months. At a 24-month horizon the error falls under 0.2%, which is arithmetic rather than virtue - the horizon and the averaging window coincide there, and that second fact is asserted precisely so the first is not read as a general result. The *unbounded* form, which is the one usually quoted as LTV, implies expected lifetimes of 50-113 months against 24 months of data, with the observed hazard still falling at the end of the window: not an arithmetic error, an extrapolation presented as a measurement.
- **The month-0 boundary is worth a test of its own**: everyone pays for month 0, since a subscriber who churns in their first month was still there for it, so the series starts at `S(-1) = 1`. Charging month 0 at `S(0)` instead loses a fraction of a month per subscriber, which on a 12-month horizon is comparable to the entire gap between two plans. Pinned with a flat survival curve where the answer is exactly `H * price`, and a second case computed by hand.
- **Which lever is bigger depends on what you are measuring, and the two reports say different things on purpose**: activity moves *retention* further than plan does (18.7 points against 7.4), which is what the planted coefficients say. It does not follow that activity moves *value* further, and at a 12-month horizon it does not - plan is worth 4.5x from cheapest to dearest at top activity while the whole activity range inside basic is worth 1.1x. Value multiplies by price; retention can only buy months, and the horizon caps how many there are to buy. Both numbers are asserted and the distinction is written into both outputs, so a reader who notices the apparent contradiction finds it already resolved instead of having to guess which figure to trust.
- **The driver model is a discrete-time logistic hazard on subscriber-months**: the generator draws a Bernoulli churn decision each month from a hazard that depends on tenure, so the subscriber-month is the unit the process actually runs on and the logit link is the *correctly specified* model for it. That is a deliberate choice in a project about verification: when the functional form is right by construction, a failure to recover the coefficients is a bug in the analysis rather than a modelling mismatch. The cost is recorded as a limitation — real data does not hand you the correct form, and nothing here exercises the case where it is wrong, beyond the `linear_tenure` comparison.
- **The day-4 result, in two halves.** Fitted on the *true* regressor (the latent engagement level, which only a test may substitute in), every coefficient comes back within 1.5 asymptotic se of its planted value: plan_standard −0.569 vs −0.45, plan_premium −1.029 vs −0.95, tenure −0.593 vs −0.55, engagement −2.382 vs −2.40, intercept −1.791 vs −1.90. Fitted on the *observable* proxy — that month's event count — the engagement coefficient attenuates to −1.383, **58% of the planted −2.40**, 8.3 standard errors away, which is bias and not noise. Reporting that as "the engagement effect" would understate the most important lever in the business by nearly half. The size is roughly what theory predicts: the reliability ratio var(e)/(var(e)+E[e]/12) = 0.0489/(0.0489+0.0427) = 0.53 against an observed 0.58, with the remainder down to the logistic link's non-linearity and the proxy being one month rather than a subscriber average. The plan and tenure terms survive, because the measurement error sits in a regressor roughly orthogonal to them.
- **A real bug: scikit-learn's default tolerance stopped the optimiser short of the MLE.** The score equation for the intercept requires `sum(y - p) = 0`; at `tol=1e-4` lbfgs left a residual of 0.98 churn events on 43,467 rows, and the coefficients were visibly off — `plan_standard` at −0.425 where the converged fit gives −0.4516 against a planted −0.45. That presents as the analysis failing to recover a coefficient, which is exactly the failure this project exists to detect, so it was worth chasing rather than shrugging at. `tol=1e-8` fixes it (`newton-cholesky` converges to the same place), and the score identity is now a test with a tolerance three orders of magnitude inside the bug. Found by checking an invariant that needs no ground truth, which is the kind that keeps working on real data.
- **Unpenalised, and spelled `C=np.inf`**: the default L2 at C=1.0 shrinks coefficients toward zero, which is harmless for prediction and wrong for a project whose point is comparing estimates against planted values — the comparison would be measuring scikit-learn's default. `penalty=None` says the same thing and emits a deprecation warning on 1.8+; both were run and agree to 1e-12.
- **Standard errors from the inverse Fisher information, not from statsmodels**: `cov = (X'WX)^-1` with `W = diag(p(1-p))` is six lines of numpy over the design matrix the fit already built, and a coefficient without a standard error cannot be compared to a planted value except by eye. Cheaper than a dependency, and the day-1 pins had already shown what carrying an unexercised package costs. Stated plainly in the output: these are asymptotic errors around the maximum-likelihood estimate and say nothing about whether the specification is right — a misspecified model gets tight errors around a wrong number.
- **Two hand-written metrics deleted the day they were written**: a clipped log-likelihood and a tie-averaged rank-sum AUC, both correct, both agreeing with scikit-learn's to 1e-12 on this data. scikit-learn was already a dependency for the model, so the hand-rolled versions were twenty lines carrying tie and degenerate-input cases they only got right by luck. Deleted.
- **Log loss, not accuracy, as the headline metric**: the monthly churn rate is 1.6%, so "nobody churns" scores 98.4% accurate. Log loss is a proper scoring rule and cannot be gamed that way. The AUC is also bounded from *above* in a test: a correctly specified model on this data scores ~0.70, and anything above 0.9 would be evidence of leakage rather than skill, because the planted hazard genuinely sits close to the base rate for most subscriber-months.
- **Calibration is tested separately from discrimination, with a mutation to prove the test bites**: tripling every predicted hazard leaves the AUC identical to 12 decimal places and moves the worst decile gap past 10 se. Held-out calibration by decile of predicted risk has a worst gap of ~2 se and most under 1. AUC says the ranking is right; only calibration says the numbers can be used for a budget or an expected-loss estimate.
- **The row-split leak, measured, and smaller than the rule suggests**: the first measurement looked like a textbook confirmation — AUC 0.711 for a random row split against 0.680 for a split by subscriber. Averaged over five seeds the gap is **0.0025** against a between-seed sd of 0.014, so that first number was the split lottery. The explanation is capacity: four parameters and no subscriber-level feature leave almost nothing to memorise. A random forest handed the subscriber id does gain a consistent 0.004-0.017 AUC from the row split, which is weak evidence from three seeds and is recorded rather than asserted. The split stays by subscriber because it is free and the harm grows with capacity — but the claim in the test is the measured one, not the textbook one.
- **Predictive scoring is a weak instrument for specification error, which is the argument for ground truth in one line**: the correctly specified model beats a linear-tenure misspecification on held-out log loss in all five seeds tried, and the margin is **0.4%**. No amount of staring at a validation score would flag that as wrong, while the coefficient on a linear tenure term means something quite different from the planted one. A single `log1p` coefficient reproducing the entire observed hazard curve (widest gap 0.69 pp at tenure 14, 1327 rows) is a far stronger check — and it agrees with day 3's risk table to floating-point equality, which also confirms both modules cover the same risk set.
- **Discrete-time Kaplan-Meier, because the data is monthly by construction**: the hazard was defined per tenure month, so the estimator works on months directly — no ties to break, no continuous-time approximation, and `S(t) = prod(1 - d_k/n_k)` over `k <= t` is exact rather than a discretisation of something else. The risk table is the load-bearing part, and the test that holds it up is the one-line identity `n(t+1) = n(t) - churned(t) - censored(t)`: a censored subscriber left in the denominator too long depresses the curve, removed too early inflates the hazard, and neither changes its shape enough to notice.
- **Censoring derived from the month rows, not read off `subscribers.censored`**: the risk table computes who leaves the risk set from `max(tenure_months)` per subscriber. Reading the generator's flag would have been one line shorter and would have made the reconciliation test — censored counts from the rows versus the flags, which agree exactly at 3315 — a comparison of a column with itself.
- **The three ways censoring gets handled wrong, each measured rather than described**: (1) "1 − churned/total" treats every censored subscriber as a permanent survivor: 82.9% against KM's 75.9% at the last observed tenure on the committed store, and it looks *better* the shorter the window, since a shorter window censors more people; (2) counting the end of observation as an exit collapses survival to 0.0%; (3) complete-case analysis — keep only subscribers with an observed churn — also gives 0.0%, by construction, since the selection is on the outcome. The third is the one that sounds most responsible ("only use complete data") and is the most badly wrong. All three are tests, so the numbers stay true as the generator changes.
- **Log-log confidence intervals rather than `S ± 1.96·se`**: the symmetric form is the one usually written and it puts the upper bound above 1 near the top of the curve, which is a claim that more than everyone survived. On the 6000-subscriber store it never actually overflows because the standard error is tiny — so the test that demonstrates it runs on a 40-subscriber store, where the symmetric bound reaches 1.023 and the log-log one stays at 0.996. Asserting the defect where it does not occur would have been a test of nothing.
- **Median survival reports "not reached"**: it is the number people ask for first, and in this dataset the curve bottoms out at 75.9% — nowhere near 0.5. The alternatives are to print the last observed tenure (wrong, and determined by window length rather than by churn) or to extrapolate the curve (an assumption dressed as a measurement). `median_survival` returns `None` and the renderer says so in words, with the lowest observed survival beside it.
- **A conservative log-rank statistic instead of a scipy dependency**: the test compares each plan's churn count with what a shared hazard would predict, `sum((O_g - E_g)^2 / E_g)` on `len(groups) - 1` df, which is the standard approximation to the full form that uses the hypergeometric covariance matrix. Two chi-square critical values are hardcoded with their source rather than installing scipy for two numbers. The trade is recorded where it matters: the simplified statistic is **conservative**, so a non-significant result from it means "not shown", not "no difference" — and that showed up in calibration, where a planted-null dataset at 2000 subscribers produced zero rejections in 20 seeds (max statistic 4.5 against a 5.991 critical value).
- **The significance test is calibrated against a planted null, not just pointed at the real data**: rebuilding the hazard with every plan effect set to zero gives a dataset where the null is true by construction. Across ten seeds the statistic ran 0.59-7.26 and crossed the critical value once — about the 5% false positive rate it should have. The assertion is therefore on the rejection *rate* (at most 2 of 10), because a test demanding zero rejections from a correctly-sized 5% test would be asserting that the test is broken. The real store, by contrast, gives chi2 = 49.3, with basic churning more than a shared hazard predicts and premium less — the direction the coefficients were planted in, which is asserted separately, since a statistic-only test passes just as happily with the groups swapped.
- **KM and the day-2 cohort curve are cross-checked against each other, offset by one month**: cohort retention at tenure t is "still subscribed at the start of month t" while KM's S(t) is "survived through month t", so retention(t) corresponds to S(t-1). They use genuinely different risk sets — the cohort curve pools only cohorts with exposure at that tenure, KM keeps everyone for the months they were observed — so agreement (0.05-1.14 se on the committed store) is evidence rather than tautology. Two estimators drifting apart would mean at least one risk set is wrong.
- **An unobservable retention cell is omitted, never zeroed**: the cohort that signed up last month cannot be observed at tenure 6, and the standard way a retention table comes out wrong is to report that cell as 0% retained instead of as unknown. It is not an obvious error to look at — retention appears to decay faster at long tenures, which reads as a finding. Measured on the 4000-subscriber 24-month store: pooled retention at tenure 12 is 82.5% done correctly and 40.5% zero-filled, and at tenure 6 87.3% against 65.7%. The matrix therefore emits only reachable cells, the pooled curve averages only over cohorts with exposure at that tenure, and a test reconstructs the zero-filled version to assert the gap is large — a comment saying "don't zero-fill" is worth nothing once someone adds a `coalesce`.
- **The headline churn rate is an exposure artifact, and that is now measured rather than asserted**: "churned subscribers / all subscribers" has a denominator that mixes populations observed for very different lengths of time. On the committed store the naive rate per cohort runs from 27.4% (signed up in month 0, a full window to churn in) to 5.5% (signed up in month 23), correlated with signup month at r = -0.86. Any real difference between those cohorts — a channel ramping up, a price change, a cheaper plan mix — would be read off this gradient and be entirely exposure. Retention at a fixed tenure removes it: the same cohorts sit within a ~6 point band with |r| < 0.5. That contrast is the argument for the whole table, so it lives in a test with the numbers in it instead of a sentence in a README that nothing checks.
- **Pooled over subscribers, not averaged over cohort rates**: at a given tenure the curve sums retained and at-risk across cohorts rather than averaging each cohort's percentage. An average of rates weights a 150-subscriber cohort the same as a 180-subscriber one, and since cohort size and exposure both vary with signup month, that bias is not random. The `cohorts` and `at_risk` columns are printed beside the rate so the pool thinning out at long tenures is visible rather than implicit — 72.6% at tenure 23 comes from one cohort of 164 and should not be read like 95.8% at tenure 1.
- **The exposure rule lives in one SQL function, `_matrix_sql`**: the matrix, the pooled curve and the per-plan curves all need the same definition of which cells are observable. Three hand-written copies would eventually disagree about which cohorts were counted, and the symptom — a curve that does not match the table it was printed next to — would not say why. The segment split is a parameter on the same query rather than a second query, with the column name checked against a `SEGMENTS` allowlist since it is interpolated into SQL.
- **Three different kinds of check on one table, because each catches what the others cannot**: (1) against the planted hazard, which catches the whole table being wrong in a consistent direction; (2) against `subscription_months`, counting "retained at tenure t" from rows written by a different part of the generator, which catches the retention convention drifting by one month — the matrix and curve would move together and agree with each other while both being wrong; (3) between cohorts at a fixed tenure, since no cohort effect was planted, which catches a per-cohort shift such as tenure being computed from the calendar month. Bounds for (3) were measured rather than guessed: worst |z| across every cell is 1.9-2.7 over seeds 67/11/404, while simulating the calendar-vs-tenure bug puts the older cohorts at 10-12 se, so a 4.5 se bound separates them. Noted honestly in the test: a *uniform* one-month shift is only ~2.5 se and is check (1)'s job, not this one's.
- **The observation window is recorded, not inferred** — reversing a call made an hour earlier the same day. The cohort code first derived the window as `max(signup_month + tenure_months) + 1`, on the reasoning that a metadata table for one integer was not worth it and that a derived value cannot drift from the rows. That reasoning has a hole: the derivation is exact only if *some* subscriber is observed to the final month. True for any realistic dataset, since most subscribers are censored — and silently wrong otherwise. Searched for a counterexample rather than assuming one existed, and found it immediately: a one-subscriber 24-month store whose only member signed up in month 15 and churned at tenure 4 reported a **20-month window**, shrinking that cohort's exposure by four months with nothing to indicate anything was wrong. Since cohort exposure is the one quantity the whole retention table rests on, an inference that is "usually right" is the wrong trade. Now a `run_meta` row carries the window alongside the subscriber count and seed, which the project wanted anyway as dataset provenance, and a missing row raises instead of defaulting. The original derivation survives as the *test* — exposure must not shrink when subscribers churn early.
- **`hazard_truth` was not the only ground truth, and the contract had a hole**: the contract as written on day 1 quarantined the *coefficients*, but `subscribers.engagement` — the latent engagement level the hazard was actually given — sits in an analysis-facing table. An analysis can therefore cheat completely without ever touching the quarantined table. This was not theoretical: swapping `order by s.engagement` in for `order by a.mean_events` in the activity-quartile cut **passed every other test in the file**, and produced a cleaner gradient, because it is reading the answer. Found by mutation-testing the new cut rather than by reasoning about it. Now guarded by the same AST mechanism, with `\bengagement\b` over the report's SQL — `_` is a word character, so `engagement_events` (the legitimate observable table) does not match while a bare column reference does, and a companion test asserts the regex still matches the real schema so the guard cannot rot silently. **Resolved on day 2: the column moves.** Surveying the actual reads first made the decision easy — the latent engagement is read *from the store* in exactly one place, and it is a test (`planted_probability`'s `select plan, engagement from subscribers`). Every other `.engagement` reference is the generator reading its own in-memory `Subscriber` dataclass, which is not the store and is not a channel an analysis can reach. So the ripple is far smaller than it looked when it was deferred: the schema, the load, and two tests.

The reason to do it rather than keep the AST guard is that the guard does not scale. It is per-module, and days 3–6 add survival analysis, a driver model and a dashboard — three more modules that each have to remember to opt into the check, where forgetting fails silently and in the direction of a better-looking result. Moving the column makes the quarantine structural: an analysis cannot read what is not in the table it queries. The AST guards stay as a second line (they also cover `hazard_truth`, which is not moving anywhere), but they stop being the only thing standing between an analysis and the answer.

Implemented the same day. The load now splits `Subscriber` on a named `LATENT_FIELDS` set rather than hand-listing each table's columns, so a field added to the dataclass lands in one table or the other automatically — and mutation-testing that found the system fails *closed*: adding an unassigned field raises a `BinderException` at load time, because `BY NAME` refuses a column the table does not have. A test also asserts the two tables partition every dataclass field, with `subscriber_id` the only legitimate overlap.

The AST guard was generalised at the same time, into `tests/test_contract.py`: analysis modules are now **discovered** (anything under `src/` not named in `GENERATOR_MODULES`) and each is parametrically checked for truth-table reads, `src.hazard` imports, and latent-column references. Proved by dropping a deliberately cheating `src/survival.py` into the tree — it was caught as `[survival]` with no edit to any test — and by dropping a clean one in, which passed. That exercise also caught a flaw in a test I had just written: pinning the discovered list to `["report"]` would have failed on every legitimate new module, which is friction rather than safety, since the parametrized guards already cover new modules. Narrowed to pinning the *exempt* side instead, where quiet growth is the actual risk. Removing the now-duplicated guards from `tests/test_report.py` deleted 104 lines.

Then a second gap in the same new guard: it scanned only `src/`, while the component table puts the day-6 Streamlit app in `dashboard/` — so the one analysis module most likely to be written quickly and least likely to be reviewed carefully would have sat entirely outside the contract. Discovery now spans both roots and reports modules as dotted paths, verified by planting a cheating `dashboard/app.py` and watching it fail as `[dashboard.app]`. A further test fails if Python appears in a directory in neither list, which generalises the mistake rather than patching this one instance of it. Worth noting that both holes in this guard were found by trying to break it, not by reading it.
- **First estimate-vs-truth result, and the shape every later one will take**: the tenure-0 monthly hazard is the cleanest possible comparison, because `log1p(0) = 0` removes the tenure term and a disagreement cannot hide in that coefficient. Taking each subscriber's own plan and engagement, asking the *stored* coefficients what their first-month churn probability was, and averaging gives 3.920%; the generated data did 3.833%, a gap of 0.34 binomial standard errors (n=6000). Rebuilding the probability from the stored rows rather than importing `src.hazard` also checks that what the store carries is usable as ground truth, not merely present. Tolerance is set at an absolute 0.01 (~4 se) — loose enough not to flake on a reseed, tight enough that a wrong exposure denominator or a dropped plan effect fails it. Checked against three seeds rather than assumed: the gap came out at 0.34, 0.67 and 1.18 se, with the plan ordering and the activity gradient holding in all three, so the result is not an artifact of the one seed the test happens to pin.
- **Exposure denominated in subscriber-months, not subscribers**: the monthly hazard divides churn events by subscriber-months *at risk*. Dividing by subscribers is the usual way this comes out wrong, since a subscriber who stayed twelve months carries twelve chances to churn but would be counted once, which deflates the hazard at exactly the long tenures where the trend is being read. Tenure 0 is the one bucket where both denominators agree (every subscriber has exactly one tenure-0 month), so a test pins it to the subscriber count there and requires the later buckets to exceed it.
- **Tenure bucketed, with the boundaries and labels generated from one tuple**: per-month hazards are too thin at the tail to read a trend off, so tenure is bucketed `0 / 1-2 / 3-5 / 6-11 / 12+`. The SQL `CASE` and the printed labels are both derived from `TENURE_BUCKETS`, because two hand-maintained copies drifting apart would silently misfile months. A test asserts no subscriber-month lands in a null bucket, that the buckets are contiguous, and that the display order follows the tuple — string ordering would print `12+` before `3-5` and show the decline out of sequence.
- **`np.random.poisson` instead of a hand-rolled sampler**: the first engagement sampler drew Poisson counts by summing exponentials until they exceeded the mean, which is correct but O(mean) per row across tens of thousands of rows. numpy was already pinned for the analysis, so the stdlib-only argument bought nothing. Changed before any dataset was committed, so no stored data had to be regenerated.
- **Bulk-load through a DataFrame scan, not `executemany`** — and a correction to the day-1 diagnosis. Day 1 recorded the slow test suite as "mostly the engagement sampler". Profiling with `--durations` said otherwise: after the numpy fix the suite was still 138s, of which 137s was two DuckDB builds (57s fixture setup, 80s rebuild test) and 0.06s the sampler. The real cause was `con.executemany("INSERT ...")`, which autocommits per statement — a 12k-row load paying 12k disk syncs. Measured on this machine, 12k rows: **34s** by `executemany`, **1.9s** wrapped in one explicit transaction, **0.06s** via `INSERT INTO ... BY NAME SELECT * FROM frame` over a pandas DataFrame. Took the DataFrame path because pandas is already a dependency for the analysis; suite went **138s → 1.4s**. `BY NAME` rather than positional `SELECT *` so a reordered dataclass field cannot shift values into the wrong column — without it, a reordered dict raises on type mismatch but a same-type swap (`engagement` vs `signup_month`) would be silent.
- **The churn month gets an engagement row** (a real bug, found while profiling, not by a failing test). `month_rows` spanned `active_months + 1` for a churned subscriber — including the month they left — while `engagement_rows` spanned only `active_months`. At 1200 subscribers that left all 162 churn rows with no matching engagement row and all 10,228 other rows with one: a **perfect separator on the target**. Day 4 would have hit it one of two ways, and the second is the dangerous one — an inner join silently drops every churn event (churn rate 0, nothing to fit), while a left join with `fillna(0)` makes "no activity" predict churn exactly, so the model reports near-perfect accuracy and a badly wrong engagement coefficient. Leakage that looks like success is the failure mode this project exists to catch, so finding it planted in the generator is the point working as intended. Fixed by giving both builders one shared span function (`recorded_months`) instead of two copies of the expression, which is what let them drift apart in the first place.
- **`frozen=True` was not enough to make the coefficients fixed**: `HazardModel` is a frozen dataclass, which blocks attribute reassignment but not mutation of the dict behind `plan_effect` — `DEFAULT_MODEL.plan_effect["premium"] = 99.0` was accepted and took a premium subscriber's monthly churn probability to 1.0. Because `DEFAULT_MODEL` is one module-level instance shared by the generator, the store and the tests, a single stray write would have moved the ground truth for all of them simultaneously, and `hazard_truth` could have been written from different coefficients than the data was drawn from — which would invalidate every estimate-vs-truth comparison while leaving the suite green. Fixed with a `__post_init__` that copies the mapping and wraps it in `MappingProxyType`; the copy closes the second route, where a caller keeps a reference to the dict they passed in. The mutation check was instructive beyond the fix: with the wrapping removed, the immutability test's own write leaked into `DEFAULT_MODEL` and broke an unrelated equality test downstream, which is the cross-contamination in miniature.
- **Distinguishing the planted effect from the artifact**: after the fix, churn-month activity still averages lower than other months — 4.87 vs 6.14 events, a 21% gap. That one is *real signal*, not leakage: low-engagement subscribers churn more, so churn months are drawn disproportionately from low-engagement subscribers. Holding engagement in a 0.4–0.6 band collapses it to 5.44 vs 5.99 (~9%, n=151, within sampling noise plus the residual selection inside the band). The leakage test asserts on the banded comparison for exactly this reason; a test on the raw means would have to either tolerate 21% (and miss a real separator) or fail on the planted effect. Day 4 has to make the same distinction, which is the whole exercise.
- **Guarding the pandas round trip with a full-equality test**: routing a nullable `churn_month` through a DataFrame makes it float64 (`None` → `NaN`), so the risks are a float leaking back out and `NaN` landing where `NULL` was meant — the second would make the censored population invisible to `is null` and quietly break every survival estimate. Rather than eyeballing one row, the test reads every stored subscriber back and compares it to the object it was generated from, types included. Both guards were mutation-checked: switching the column to `DOUBLE` fails the round-trip test, and dropping `BY NAME` with reordered keys raises.
